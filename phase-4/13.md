## 1. Why deployment strategies exist

Welcome to **Phase 13**, the first phase of Level 4 — Production Engineering.

In Phase 12, we built the complete delivery chain:

```text
Developer
   |
   v
Git
   |
   v
GitHub Actions
   |
   v
Validated Container Image
   |
   v
Container Registry
   |
   v
GitOps Release Approval
   |
   v
Argo CD
   |
   v
Kubernetes
   |
   v
Running Application
```

We now know how to deliver a specific, approved artifact to Kubernetes.

But a new problem appears.

**What happens to the users already using the application while Kubernetes replaces the old version with the new one?**

Suppose our e-commerce API currently serves 10,000 requests per minute.

Production runs:

```text
Application version: v1

Replicas: 4

Status: Healthy
```

CI builds and validates version `v2`.

Release Engineering authorizes the deployment.

Argo CD updates the desired image reference.

Now Kubernetes must replace the running instances.

We have several questions:

- Should all four old Pods stop simultaneously?
- Should new Pods become ready before old Pods terminate?
- Can old and new versions safely run together?
- How much additional capacity is available?
- How many users should encounter the new version initially?
- How do we determine whether the new version is healthy?
- What happens if the new version fails halfway through deployment?
- Can we restore the previous version?
- Can the database support both application versions during the transition?

These are not primarily GitHub Actions questions.

They are **deployment strategy questions**.

### Central engineering question

> **How do we move a running system from version A to version B while controlling availability, compatibility, user exposure, resource consumption, and recovery risk?**

This phase will teach you to choose and implement deployment strategies from requirements—not memorize strategy names.

# Part I — First-Principles Thinking

## 3. Deployment is a transition between two operating states

Imagine an application serving users.

At time T1:

```text
Desired Application: v1
Running Application: v1
```

After a release, we want:

```text
Desired Application: v2
Running Application: v2
```

But the system cannot necessarily transition instantaneously.

There may be an intermediate period:

```text
Running:
v1 and v2
```

Or:

```text
Running:
No application instances
```

The deployment strategy determines which intermediate states are permitted.

### A state-transition model

```mermaid
flowchart TD
    A["Stable System Running v1"]
    B["Release v2 Authorized"]
    C["Deployment Strategy"]
    D["Intermediate Runtime States"]
    E["Verification"]
    F{"Transition Acceptable?"}
    G["Stable System Running v2"]
    H["Stop or Recover"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F

    F -->|Yes| G
    F -->|No| H
```

This is the first important realization:

**A deployment strategy is a policy for managing intermediate states.**

It controls how an old version is replaced, how users encounter the new version, and what happens when the transition is unsuccessful.

## 4. Derive the fundamental deployment requirements

Before choosing a strategy, identify the requirements.

Consider six dimensions.

| Dimension | Engineering question |
|---|---|
| Availability | How much service interruption is acceptable? |
| Compatibility | Can old and new versions coexist? |
| Capacity | How many additional Pods can the cluster run? |
| Exposure | How many users may encounter the new version initially? |
| Verification | What evidence determines whether the new version is acceptable? |
| Recovery | How can the system return to acceptable behavior? |

These dimensions determine our strategy.

### Example A — Internal development application

Requirements:

```text
Downtime: Acceptable

Additional capacity: Limited

Release frequency: Low

Mixed versions: Not required
```

A **Recreate** deployment might be reasonable.

### Example B — Customer-facing API

Requirements:

```text
Downtime: Unacceptable under normal conditions

Additional capacity: Available

Old/new coexistence: Supported

Release frequency: High
```

A **RollingUpdate** may be sufficient.

### Example C — High-risk payment service

Requirements:

```text
Downtime: Minimize

New-version exposure: Gradual

Operational verification: Required

Ability to stop promotion: Required
```

A **Canary** strategy with appropriate traffic routing and analysis may be preferable.

### Example D — Application requiring full preview testing

Requirements:

```text
Test complete new environment first

Keep current version serving users

Switch traffic after authorization
```

A **Blue-Green** strategy may fit.

### First-principles rule

> **Choose a deployment strategy according to failure tolerance and transition requirements, not because one strategy sounds more advanced.**

## 5. What does zero downtime really mean?

You will frequently hear:

> Kubernetes supports zero-downtime deployment.

That statement requires qualifications.

A Kubernetes strategy can help preserve available replicas during an update.

But zero user-visible downtime also depends on:

- Sufficient application capacity.
- Correct readiness probes.
- Reliable network routing.
- Graceful shutdown behavior.
- Compatible application versions.
- Compatible databases and APIs.
- Available cluster resources.
- No external dependency failures.

### Example

Suppose we run four Pods.

Each can handle 100 requests per second.

Our theoretical maximum capacity is:

```text
4 × 100 = 400 requests/second
```

Now traffic reaches 350 requests per second.

If we terminate one Pod without replacing its capacity, the remaining three Pods can theoretically handle:

```text
3 × 100 = 300 requests/second
```

The application may become overloaded.

Even though three Pods remain running.

The numbers are simplified; real throughput depends on workload, latency, resource allocation, and traffic distribution.

### Availability is not merely Pod count

```text
Running Pods
      !=
Available Application Capacity
```

Likewise:

```text
Ready Pods
      !=
Guaranteed Successful User Requests
```

### Important principle

**A safe deployment needs sufficient healthy serving capacity throughout the transition, not just a configuration that requests multiple replicas.**

## 6. The lifecycle of a Pod during deployment

We cannot design deployment strategies properly without understanding Pod lifecycle.

Consider a new container.

It moves through several stages:

```mermaid
flowchart TD
    A["Pod Created"]
    B["Pod Scheduled"]
    C["Image Available"]
    D["Container Starts"]
    E["Startup Requirements Satisfied"]
    F["Readiness Check Passes"]
    G["Pod Becomes Ready"]
    H["Service May Route Traffic"]
    I["Pod Eventually Terminates"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H
    H --> I
```

Not every application requires a startup probe.

The diagram shows the logical stages rather than claiming Kubernetes always configures all three probe types.

### Why does this matter?

A container can be running without being ready to receive traffic.

For example:

```text
Container process:
Running
```

But:

```text
Database connection:
Not initialized
```

A readiness probe should prevent that Pod from being considered a ready Service endpoint when the required serving conditions are not satisfied.

This is a critical component of safe deployments.

## 7. Liveness, readiness, and startup probes

These checks answer different questions.

### Liveness

**Should Kubernetes restart this container because its process is no longer operating acceptably?**

Example:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 3000
```

A repeatedly failing liveness probe can cause the container to restart.

A liveness probe should not be made dependent on every external service in a way that creates cascading restarts during a dependency outage.

### Readiness

**Should this Pod currently receive normal Service traffic?**

Example:

```yaml
readinessProbe:
  httpGet:
    path: /readyz
    port: 3000
```

When readiness fails, the Pod is not considered ready for normal Service endpoint routing.

This is particularly important while introducing a new version.

### Startup

**Has the application completed its startup period?**

Example:

```yaml
startupProbe:
  httpGet:
    path: /healthz
    port: 3000
  periodSeconds: 2
  failureThreshold: 30
```

A startup probe gives applications time to initialize before normal liveness and readiness probing proceeds.

### Comparison

| Probe | Main purpose | Typical response to failure |
|---|---|---|
| Startup | Determine whether initialization completed | Eventually restart on repeated failure |
| Readiness | Determine whether Pod should receive traffic | Remove from ready endpoints |
| Liveness | Determine whether the container should be restarted | Restart on repeated failure |

Kubernetes documents these differences in its [probe configuration guide](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).

### The deployment implication

> **A rolling or progressive deployment cannot protect user availability reliably if readiness does not represent the application's ability to serve the relevant requests.**

## 8. Graceful termination matters as much as startup

Suppose a Pod is serving a customer request.

Kubernetes decides to terminate the Pod.

If the application immediately exits, the request may fail.

A safer termination process is:

1. Stop advertising the terminating Pod for new traffic.
2. Allow routing changes to propagate.
3. Stop accepting new requests when appropriate.
4. Complete or safely terminate in-flight work.
5. Exit before the termination grace period expires.

### Termination sequence

```mermaid
flowchart TD
    A["Pod Termination Requested"]
    B["Pod Becomes Terminating"]
    C["Endpoint Routing Updates"]
    D["Application Receives Termination Signal"]
    E["Stop Accepting New Work"]
    F["Finish or Safely Interrupt Existing Work"]
    G["Container Exits"]

    A --> B
    B --> C
    B --> D
    D --> E
    E --> F
    F --> G
```

The endpoint updates and termination signals do not necessarily happen in a perfectly serialized order. Routing changes and connection draining can take time.

This is why production applications often need explicit graceful-shutdown handling.

### Node.js example

```javascript
const server = app.listen(3000);

process.on("SIGTERM", () => {
  server.close((error) => {
    if (error) {
      process.exitCode = 1;
    }
  });
});
```

This is a simplified example.

Real applications may also need to stop accepting background jobs, manage long-lived connections, flush telemetry, and coordinate with database transactions.

### Core lesson

**Starting new Pods safely and terminating old Pods safely are equally important parts of deployment reliability.**

# Part II — Deployment Strategies From First Principles

## 9. Strategy 1 — Recreate

Begin with the simplest replacement strategy.

Suppose production runs:

```text
v1
v1
v1
```

We want:

```text
v2
v2
v2
```

One approach is:

1. Stop the old Pods.
2. Wait for them to terminate.
3. Start the new Pods.
4. Wait for readiness.

This is the **Recreate** strategy.

### Architecture

```mermaid
flowchart TD
    A["Three Ready v1 Pods"]
    B["Terminate Old Pods"]
    C["No Replacement Pods Ready"]
    D["Create v2 Pods"]
    E["Wait for Readiness"]
    F["Three Ready v2 Pods"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
```

Kubernetes defines Recreate as terminating the old Pods before creating the new Pods during a Deployment update. [Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/?utm_source=chatgpt.com)

### Advantages

- Simple lifecycle.
- No planned overlap of old and new Pod versions during the replacement.
- Limited additional Pod capacity required.
- Useful when simultaneous application versions are unsafe.

### Disadvantages

- Creates an availability gap if the application has no alternate serving instances.
- Restart time becomes user-visible.
- A failed new version can extend the outage.
- May be unsuitable for customer-facing systems.

### Kubernetes configuration

```yaml
strategy:
  type: Recreate
```

### When would you select it?

Potentially for:

- Disposable development applications.
- Scheduled maintenance jobs.
- Certain non-HA applications.
- Systems where mixed-version operation is prohibited and interruption is acceptable.

### Important nuance

Recreate does not guarantee that there is only one executing process across every external system.

It governs the Deployment's Pod replacement behavior.

Distributed coordination may still be required for exclusive workers or stateful applications.

## 10. Strategy 2 — RollingUpdate

Now suppose downtime is unacceptable under normal operating conditions.

Instead of stopping all old Pods together, we gradually replace them.

Initial state:

```text
v1 v1 v1 v1
```

Intermediate state:

```text
v1 v1 v1 v1 + v2 starting
```

After readiness:

```text
v1 v1 v1 v2
```

Eventually:

```text
v2 v2 v2 v2
```

This is a **RollingUpdate**.

### Architecture

```mermaid
flowchart TD
    A["Four Ready v1 Pods"]
    B["Start One v2 Pod"]
    C["Wait for v2 Readiness"]
    D["Remove One v1 Pod"]
    E["Repeat Replacement"]
    F["Four Ready v2 Pods"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
```

### Why does this help?

Because available old instances can continue serving traffic while new instances start.

Kubernetes supports configurable limits on additional Pods and unavailable Pods during rolling updates. [Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/?utm_source=chatgpt.com)

But we need to understand those limits mathematically.

---

## 11. Rolling deployments: `maxSurge`

Suppose:

```text
Desired replicas = 4
```

We configure:

```yaml
maxSurge: 1
```

This permits the controller to create up to one additional non-terminating Pod beyond the desired count during the rollout, subject to its rollout calculations.

Conceptually:

```text
Desired Replicas:
4
```

```text
Maximum Active Replica Budget:
4 + 1 = 5
```

The cluster therefore needs sufficient capacity for the additional Pod.

### Why is this important?

Imagine the cluster can run exactly four application Pods.

A rollout requesting a fifth Pod may be blocked by:

```text
Insufficient CPU
```

Or:

```text
Insufficient memory
```

The new Pod cannot start.

The rollout may stall.

### Engineering trade-off

Higher `maxSurge` can increase rollout speed, but requires additional temporary capacity.

---

## 12. Rolling deployments: `maxUnavailable`

Now consider:

```yaml
maxUnavailable: 0
```

For four desired replicas, the rolling-update controller attempts to preserve at least four available replicas throughout the rollout.

Conceptually:

```text
Desired Replicas:
4
```

```text
Minimum Available Replicas:
4 - 0 = 4
```

This is a useful setting for availability-sensitive services when sufficient capacity exists.

### Complete example

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

### What does this protect against?

It prevents the Deployment controller from intentionally reducing available replica capacity below its configured threshold as part of the rolling-update algorithm.

### What does it not guarantee?

- New Pods can actually be scheduled.
- All four Pods will remain healthy despite unrelated failures.
- Traffic is evenly distributed.
- Every request succeeds.
- Application versions are database-compatible.
- The load balancer drains every connection perfectly.

### Important capacity nuance

Terminating Pods can temporarily remain in the cluster while replacements exist, so actual resource consumption can exceed the simple `replicas + maxSurge` calculation during termination. [Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/?utm_source=chatgpt.com)

### Practical interpretation

`maxSurge` controls temporary replacement capacity.

`maxUnavailable` controls how much rollout-related availability reduction is permitted.

They solve different problems.

---

## 13. RollingUpdate numerical exercises

Let's reason about three configurations.

Assume four desired replicas.

| Configuration | Temporary surge budget | Minimum available replicas during update |
|---|---:|---:|
| `maxSurge: 1`, `maxUnavailable: 0` | 1 | 4 |
| `maxSurge: 0`, `maxUnavailable: 1` | 0 | 3 |
| `maxSurge: 2`, `maxUnavailable: 1` | 2 | 3 |

These describe the controller's configured rollout constraints, not guarantees against external failures.

### Scenario A — Prioritize availability

Choose:

```yaml
maxSurge: 1
maxUnavailable: 0
```

Why?

You want to avoid planned capacity reduction while replacing Pods.

### Scenario B — Strict resource budget

Choose:

```yaml
maxSurge: 0
maxUnavailable: 1
```

Why?

You cannot create additional Pods.

But you accept temporarily reduced available capacity.

### Scenario C — Prioritize rollout speed

Choose:

```yaml
maxSurge: 2
maxUnavailable: 1
```

Why?

You allow more simultaneous replacement activity.

### Engineering question

Which is best?

There is no universal answer.

You need to know:

- The application's spare capacity.
- Request rate.
- Startup duration.
- Resource quotas.
- Node capacity.
- Availability objective.
- Cost constraints.

This is why deployment configuration is a system-design decision.

## 14. What happens when a rolling update fails?

Imagine:

```text
v1 Pods:
Healthy
```

But the new `v2` Pods fail readiness.

With:

```yaml
maxSurge: 1
maxUnavailable: 0
```

The controller can create a new Pod without deliberately terminating available old capacity.

If the new Pod never becomes available, rollout progress may stop.

### Failure state

```mermaid
flowchart TD
    A["Old v1 Pods Healthy"]
    B["Create New v2 Pod"]
    C["v2 Readiness Fails"]
    D["New Pod Not Available"]
    E["Rollout Cannot Progress Normally"]
    F["Investigate and Recover"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
```

### Important Kubernetes behavior

A Deployment can report:

```text
ProgressDeadlineExceeded
```

when it does not make adequate progress before its configured deadline.

But **Kubernetes does not automatically roll the Deployment back merely because this condition appears**. The controller continues retrying, and a higher-level system or operator must decide what to do. [Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/?utm_source=chatgpt.com)

This is a very important distinction.

**Failure detection is not automatically failure recovery.**

## 15. Strategy 3 — Blue-Green

Now consider a different requirement.

The team wants to validate a fully provisioned new version before sending normal user traffic to it.

Instead of gradually replacing old Pods, we maintain two environments or two sets of application instances.

**Blue:** Currently serving users.

**Green:** New version being prepared.

### Architecture

```mermaid
flowchart TD
    A["Users"]
    B["Active Service"]
    C["Blue v1 Pods"]

    D["Preview Service"]
    E["Green v2 Pods"]
    F["Preview Verification"]
    G["Promotion Authorization"]

    A --> B
    B --> C

    D --> E
    E --> F
    F --> G

    G -.->|"Switch active routing to Green"| B
```

### Phase 1 — Prepare

Blue serves users.

Green starts separately.

### Phase 2 — Verify

Tests run against Green through a preview endpoint.

Blue continues serving users.

### Phase 3 — Promote

The active routing target changes to Green.

### Phase 4 — Retain or remove old capacity

Blue may remain available temporarily for rapid recovery before being scaled down.

### Advantages

- New version can be tested before promotion.
- Clear separation of active and preview instances.
- Routing changes can move users to the new version.
- Previous serving capacity may be retained temporarily.

### Disadvantages

- Often requires roughly double application capacity during preview.
- The traffic switch does not make all existing connections disappear instantaneously.
- Database and shared-state compatibility remain necessary.
- A bad routing configuration can cause an outage.
- Running both versions may have meaningful cost.

### Important principle

> **Blue-green reduces the risk of replacing serving instances before verifying replacements, but it does not eliminate compatibility, routing, or data-state risks.**

Argo Rollouts implements blue-green behavior using an `activeService` and optionally a `previewService`. [Argo Project](https://argoproj.github.io/argo-rollouts/features/bluegreen/?utm_source=chatgpt.com)

## 16. Strategy 4 — Canary

Now consider this requirement:

> We want to expose a new version to a small portion of traffic, observe its behavior, and expand exposure only when the evidence is acceptable.

This is a **Canary** deployment.

Instead of switching all traffic immediately, we progressively introduce the new version.

Conceptually:

```text
Stage 1:
5% new version
95% old version
```

```text
Stage 2:
20% new version
80% old version
```

```text
Stage 3:
50% new version
50% old version
```

```text
Stage 4:
100% new version
```

These are conceptual traffic targets. Achieving precise weights requires appropriate traffic-routing capabilities.

### Architecture

```mermaid
flowchart TD
    A["User Traffic"]
    B["Traffic Distribution"]
    C["Stable v1"]
    D["Canary v2"]

    E["Canary Metrics"]
    F{"Acceptance Policy Passed?"}
    G["Increase Canary Exposure"]
    H["Stop or Abort Rollout"]
    I["Promote v2 to Stable"]

    A --> B
    B --> C
    B --> D

    D --> E
    C --> E

    E --> F

    F -->|Yes| G
    F -->|No| H

    G --> I
```

### What does canary protect against?

It limits the initial number of users or requests exposed to an unproven release.

It gives the team an opportunity to evaluate real runtime behavior before full promotion.

### What does it not guarantee?

- The canary receives sufficient representative traffic.
- The metrics are statistically meaningful.
- A rare defect is detected.
- The rollout will stop without properly configured gates.
- The system can safely restore the previous version after a database change.

### The deeper principle

**Canary deployment trades rollout speed and operational complexity for controlled exposure and additional real-world evidence.**

---

## 17. A critical canary distinction: Pods are not traffic percentages

This is one of the easiest deployment concepts to misunderstand.

Suppose we have five replicas.

Our canary strategy requests:

```text
20% Canary
```

Without an external traffic router, Argo Rollouts can approximate the target by managing replica counts.

For five replicas:

```text
Stable Pods:
4
```

```text
Canary Pods:
1
```

The intended approximation is:

```text
1 / 5 = 20%
```

But does that guarantee exactly 20% of HTTP requests reach the canary?

**No.**

Traffic distribution can vary because of:

- Long-lived connections.
- Unequal request rates.
- Session affinity.
- Endpoint selection.
- Small sample sizes.
- Differences between connection distribution and request distribution.

Argo Rollouts explicitly describes its basic no-router canary mode as a best-effort approximation using ReplicaSet proportions. [Argo Project](https://argoproj.github.io/argo-rollouts/features/canary/?utm_source=chatgpt.com)

### Example

With five replicas, requesting:

```text
10% Canary
```

cannot be represented exactly by one new Pod.

One of five is already 20%.

### How do we gain finer control?

Use an appropriate traffic-routing integration, such as a supported ingress controller, gateway, or service mesh.

Then traffic weight and replica count can be controlled more independently.

### Important distinction

```text
20% New Pods
       !=
Guaranteed 20% of Requests
```

This distinction matters in production architecture interviews.

---

## 18. Canary is not just gradual deployment

A weak canary system does this:

```text
Deploy 10%
Wait 2 minutes
Deploy 50%
Wait 2 minutes
Deploy 100%
```

What is missing?

**Evidence.**

Time passing is not proof that the application is healthy.

A stronger system evaluates conditions such as:

- Error rate.
- Request latency.
- Timeout rate.
- Availability.
- Application-specific business errors.
- Dependency failure rates.
- Resource saturation.

### Progressive delivery

Progressive delivery combines controlled exposure with evidence-based progression.

```mermaid
flowchart TD
    A["Canary Exposure"]
    B["Collect Runtime Measurements"]
    C["Evaluate Acceptance Criteria"]
    D{"Metrics Acceptable?"}
    E["Advance Exposure"]
    F["Pause or Abort"]
    G["Repeat Until Fully Promoted"]

    A --> B
    B --> C
    C --> D

    D -->|Yes| E
    D -->|No| F

    E --> G
    G --> B
```

This is why Argo Rollouts supports AnalysisTemplates and AnalysisRuns that can evaluate metrics while a rollout progresses. [Argo Project](https://argoproj.github.io/argo-rollouts/features/analysis/?utm_source=chatgpt.com)

## 19. Choosing the strategy: a decision table

| Requirement | Recreate | Rolling | Blue-Green | Canary |
|---|---|---|---|---|
| Minimize normal deployment downtime | Poor fit | Good fit | Good fit | Good fit |
| Avoid simultaneous old/new versions | Good fit | Poor fit | Poor fit | Poor fit |
| Minimize extra capacity | Good fit | Depends on surge | Usually expensive | Depends on mode |
| Preview complete new version | Limited | Limited | Strong | Possible |
| Limit initial user exposure | No | Limited | Usually all at switch | Strong |
| Gradually increase exposure | No | Pod replacement | Usually no | Yes |
| Requires advanced traffic routing | No | No | Not necessarily | For precise weighting |
| Operational complexity | Low | Moderate | Higher | Higher |
| Typical Kubernetes implementation | Deployment | Deployment | Argo Rollouts or equivalent | Argo Rollouts or equivalent |

### How to make a choice

Ask these questions in order:

1. Can old and new application versions coexist safely?
2. Is service interruption acceptable?
3. How much temporary capacity is available?
4. Is pre-promotion testing required?
5. Is limited user exposure required?
6. Can we collect reliable rollout metrics?
7. What recovery options are available?

Then choose the least complicated strategy satisfying the requirements.

# Part III — Argo CD and Argo Rollouts

## 20. Why Argo CD alone is not a complete progressive-delivery engine

We already use Argo CD.

Why introduce Argo Rollouts?

Because the two systems solve different problems.

### Argo CD

Answers:

> Does the Kubernetes configuration match the authorized desired state in Git?

For example, Git declares:

```yaml
image: ghcr.io/example/api@sha256:...
```

Argo CD identifies whether the corresponding Kubernetes resource configuration matches that declaration.

It can reconcile approved changes according to policy.

### Argo Rollouts

Answers:

> How should the running application transition from the old version to the new version?

For example:

```text
Start 20% Canary
       |
       v
Pause
       |
       v
Evaluate Runtime Behavior
       |
       v
Promote or Abort
```

### Relationship

```mermaid
flowchart TD
    A["Approved GitOps Repository"]
    B["Argo CD"]
    C["Kubernetes Rollout Resource"]
    D["Argo Rollouts Controller"]

    E["Stable ReplicaSet"]
    F["Canary ReplicaSet"]
    G["Service Routing"]
    H["Runtime Analysis"]

    A --> B
    B --> C
    C --> D

    D --> E
    D --> F
    D --> G

    E --> H
    F --> H
```

This is the central distinction:

**Argo CD manages declarative desired state.**

**Argo Rollouts manages progressive transitions between application versions.**

They are complementary rather than interchangeable.

Argo Rollouts can also operate without Argo CD; it is a standalone Kubernetes controller. [Argo Project](https://argoproj.github.io/argo-rollouts/FAQ/?utm_source=chatgpt.com)

---

## 21. What is an Argo Rollouts `Rollout` resource?

A Kubernetes `Deployment` manages ReplicaSets and Pod replacement.

Argo Rollouts introduces another workload custom resource:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
```

This resource can define:

- Application replicas.
- Container image.
- Pod template.
- Canary steps.
- Blue-green services.
- Promotion pauses.
- Analysis requirements.
- Recovery-related behavior.

### Compare the resources

| Kubernetes Deployment | Argo Rollouts Rollout |
|---|---|
| Built-in Kubernetes resource | Custom resource supplied by Argo Rollouts |
| Managed by Deployment controller | Managed by Argo Rollouts controller |
| RollingUpdate and Recreate | Canary and blue-green strategies |
| Basic rollout controls | Progressive rollout steps and pauses |
| Kubernetes rollout status | Rollout status and optional analysis |
| No native metric-based canary progression | Analysis integration available |

### Important architectural boundary

For a particular workload, don't deploy an ordinary Deployment and an Argo Rollouts Rollout with overlapping selectors that independently manage the same Pods.

They would become competing workload controllers.

A strategy change from Deployment to Rollout is a **resource-ownership migration**, not merely an image change.

## 22. Three separate decisions in progressive delivery

We should distinguish:

### Decision A — Is this release authorized?

Owned by:

```text
Release Engineering
```

Evidence might include:

```text
Approved GitOps Pull Request
```

### Decision B — How should the release progress?

Owned by:

```text
Deployment Strategy Configuration
```

For example:

```text
20% Canary

Pause

40% Canary

Pause

100% Promotion
```

### Decision C — Should progression continue?

Owned by:

```text
Rollout Analysis or Authorized Operator
```

For example:

```text
Error rate below threshold?

Latency acceptable?

Business transactions functioning?
```

### Complete control structure

```mermaid
flowchart TD
    A["Published Artifact"]
    B["Release Authorization"]
    C["Approved GitOps Change"]
    D["Argo CD"]
    E["Argo Rollouts"]
    F["Initial Exposure"]
    G["Analysis or Operator Decision"]
    H{"Safe to Continue?"}
    I["Increase Exposure"]
    J["Pause or Abort"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H

    H -->|Yes| I
    H -->|No| J
```

### Fundamental insight

> **Authorization controls which release may be introduced. Deployment strategy controls how it is introduced. Analysis controls whether introduction should continue.**

## 26. Create the demonstration application

Create:

```text
demo/server.js
```

Add:

```javascript
const http = require("node:http");
const os = require("node:os");

const VERSION = process.env.APP_VERSION || "v1";

const FAIL_READINESS =
  process.env.FAIL_READINESS === "true";

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "application/json");

  if (req.url === "/healthz") {
    res.writeHead(200);
    res.end(JSON.stringify({ status: "alive" }));
    return;
  }

  if (req.url === "/readyz") {
    const status = FAIL_READINESS ? 503 : 200;

    res.writeHead(status);

    res.end(
      JSON.stringify({
        ready: !FAIL_READINESS,
        version: VERSION
      })
    );

    return;
  }

  if (req.url === "/version") {
    res.writeHead(200);

    res.end(
      JSON.stringify({
        version: VERSION,
        pod: os.hostname()
      })
    );

    return;
  }

  res.writeHead(404);
  res.end(JSON.stringify({ error: "Not Found" }));
});

server.listen(3000, "0.0.0.0", () => {
  console.log(`Application ${VERSION} listening`);
});

process.on("SIGTERM", () => {
  console.log("SIGTERM received");

  server.close(() => {
    console.log("HTTP server closed");
  });
});
```

### Why this application?

Because it exposes three useful behaviors.

| Endpoint | Purpose |
|---|---|
| `/healthz` | Process liveness |
| `/readyz` | Serving readiness |
| `/version` | Identify which application version responded |

It also supports intentional readiness failures.

### Why include the hostname?

Because Kubernetes assigns different hostnames to different Pods.

The response helps us observe which Pod handled a request.

### Why include SIGTERM handling?

Because we want to demonstrate that old containers can close their HTTP server during termination.

This is not a complete production shutdown implementation, but it exposes the relevant lifecycle mechanism.

# Part V — Experiment 1: RollingUpdate

## 30. Define the rolling deployment

Create:

```text
rolling/deployment.yaml
```

Add:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rolling-demo
  namespace: delivery-strategies-lab
spec:
  replicas: 3

  revisionHistoryLimit: 5
  progressDeadlineSeconds: 60
  minReadySeconds: 3

  selector:
    matchLabels:
      app: rolling-demo

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

  template:
    metadata:
      labels:
        app: rolling-demo

    spec:
      terminationGracePeriodSeconds: 30

      containers:
        - name: api
          image: rollout-lab:v1
          imagePullPolicy: IfNotPresent

          ports:
            - name: http
              containerPort: 3000

          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            periodSeconds: 2
            failureThreshold: 2

          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 5

          resources:
            requests:
              cpu: 25m
              memory: 32Mi
            limits:
              cpu: 250m
              memory: 128Mi

---
apiVersion: v1
kind: Service
metadata:
  name: rolling-demo
  namespace: delivery-strategies-lab
spec:
  selector:
    app: rolling-demo

  ports:
    - port: 80
      targetPort: 3000
```

### Understand the design

**Three replicas:** Enough to observe gradual replacement.

**`maxSurge: 1`:** Permit an additional Pod during the transition.

**`maxUnavailable: 0`:** Preserve the desired available replica count during normal rolling replacement.

**`minReadySeconds: 3`:** Require a Pod to remain ready for a short period before considering it available for rollout calculations.

**`progressDeadlineSeconds: 60`:** Define when the rollout should report inadequate progress.

**Readiness probe:** Prevent unhealthy new Pods from becoming ready Service endpoints.

**Liveness probe:** Detect an unresponsive application process.

## 38. Create a blue-green Rollout

Create:

```text
bluegreen/rollout.yaml
```

Add:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: bluegreen-demo
  namespace: delivery-strategies-lab
spec:
  replicas: 2
  revisionHistoryLimit: 3

  selector:
    matchLabels:
      app: bluegreen-demo

  template:
    metadata:
      labels:
        app: bluegreen-demo

    spec:
      containers:
        - name: api
          image: rollout-lab:v1
          imagePullPolicy: IfNotPresent

          ports:
            - containerPort: 3000

          readinessProbe:
            httpGet:
              path: /readyz
              port: 3000
            periodSeconds: 2

          resources:
            requests:
              cpu: 25m
              memory: 32Mi

  strategy:
    blueGreen:
      activeService: bluegreen-active
      previewService: bluegreen-preview
      autoPromotionEnabled: false
      scaleDownDelaySeconds: 30

---
apiVersion: v1
kind: Service
metadata:
  name: bluegreen-active
  namespace: delivery-strategies-lab
spec:
  selector:
    app: bluegreen-demo

  ports:

---
apiVersion: v1
kind: Service
metadata:
  name: bluegreen-preview
  namespace: delivery-strategies-lab
spec:
  selector:
    app: bluegreen-demo

  ports:
    - port: 80
      targetPort: 3000
```

### What is special about this manifest?

Notice:

```yaml
strategy:
  blueGreen:
    activeService: bluegreen-active
    previewService: bluegreen-preview
    autoPromotionEnabled: false
```

These are the important fields.

### `activeService`

Selects the currently active application revision.

### `previewService`

Provides an endpoint for the new revision before it is promoted.

### `autoPromotionEnabled: false`

Stops automatic promotion of an updated, ready preview revision.

An authorized operator or process must promote it.

### `scaleDownDelaySeconds`

Keeps the previous active ReplicaSet available temporarily after the traffic switch.

This can help accommodate routing propagation and recovery considerations.

Argo Rollouts documents this blue-green lifecycle and Service behavior. [Argo Project](https://argoproj.github.io/argo-rollouts/features/bluegreen/?utm_source=chatgpt.com)

## 45. Create the canary Rollout

Create:

```text

```

Add:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: canary-demo
  namespace: delivery-strategies-lab
spec:
  replicas: 5
  revisionHistoryLimit: 3

  selector:
    matchLabels:
      app: canary-demo

  template:
    metadata:
      labels:
        app: canary-demo

    spec:
      containers:
        - name: api
          image: rollout-lab:v1
          imagePullPolicy: IfNotPresent

          ports:
            - containerPort: 3000

          readinessProbe:
            httpGet:
              path: /readyz
              port: 3000
            periodSeconds: 2

          resources:
            requests:
              cpu: 25m
              memory: 32Mi

  strategy:
    canary:
      maxSurge: 1
      maxUnavailable: 0

      steps:
        - setWeight: 20
        - pause: {}

        - setWeight: 40
        - pause: {}

        - setWeight: 100

---
apiVersion: v1
kind: Service
metadata:
  name: canary-demo
  namespace: delivery-strategies-lab
spec:
  selector:
    app: canary-demo

  ports:
    - port: 80
      targetPort: 3000
```

In this no-router setup, Argo Rollouts uses ReplicaSet scaling to approximate the requested exposure weight.

It creates an indefinite pause.

The rollout requires a promotion action to continue.

### Why not automatically promote after a fixed duration?

Because we want to introduce an explicit verification decision.

### Important limitation

We have not configured automated metric analysis.

# Part IX — Metrics-Driven Progressive Delivery

## 50. Why pauses alone are not enough

Suppose a canary has been running for five minutes.

No engineer has reported a problem.

Is it safe to promote?

Not necessarily.

The absence of a human complaint is weak evidence.

We need defined acceptance conditions.

### Example policy

```text
HTTP 5xx Error Rate:
Below 1%
```

```text
P95 Request Latency:
Below 300 ms
```

```text
Critical Business Operations:
Successful
```

```text
Minimum Observations:
Sufficient to support a meaningful decision
```

These are example thresholds. Appropriate values depend on the application's service objectives and workload.

### The deeper problem

A monitoring metric tells us what was measured.

A release policy tells us how to interpret it.

We need both.

---

## 51. Derive an analysis-based canary gate

A useful progressive-delivery gate has five parts.

**1. Measurement source**

Where does the data come from?

For example:

```text
Prometheus
```

**2. Target population**

Which requests are being evaluated?

For example:

```text
Canary API Requests
```

**3. Observation window**

Over what period?

For example:

```text
Last 5 Minutes
```

**4. Acceptance condition**

What result is acceptable?

For example:

```text
Success Rate >= 99%
```

**5. Failure policy**

What happens when the condition fails or measurements are unavailable?

For example:

```text
Pause or Abort
```

### Control architecture

```mermaid
flowchart TD
    A["Canary Version"]
    B["Application Metrics"]
    C["Prometheus"]
    D["AnalysisRun"]
    E["Evaluate Acceptance Criteria"]
    F{"Result"}
    G["Continue Promotion"]
    H["Abort or Stop"]
    I["Pause for Investigation"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F

    F -->|Successful| G
    F -->|Failed| H
    F -->|Inconclusive| I
```

Argo Rollouts supports `AnalysisTemplate`, `AnalysisRun`, and several metric providers for this purpose. [Argo Project](https://argoproj.github.io/argo-rollouts/features/analysis/?utm_source=chatgpt.com)

---

## 52. Example AnalysisTemplate

This is an architectural example, not part of the base executable lab.

It assumes:

- A working Prometheus server.
- Correctly instrumented application metrics.
- A query that returns the expected result.
- Appropriate label values.
- Sufficient traffic for analysis.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: api-success-rate
spec:
  metrics:
    - name: success-rate
      interval: 1m
      count: 5
      failureLimit: 1

      successCondition: result[0] >= 0.99

      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090

          query: |
            sum(
              rate(
                http_requests_total{
                  service="ecommerce-api",
                  version="v2",
                  status!~"5.."
                }[5m]
              )
            )
            /
            sum(
              rate(
                http_requests_total{
                  service="ecommerce-api",
                  version="v2"
                }[5m]
              )
            )
```

### Understand the design

The query estimates the fraction of observed requests that did not return HTTP 5xx responses.

The analysis condition requires:

```text
Success Rate >= 99%
```

### What could go wrong?

- The application does not expose this metric.
- Label names differ.
- There is insufficient traffic.
- The denominator is zero.
- Prometheus is unavailable.
- Measurements are delayed.
- HTTP success does not imply business success.

An undefined, empty, or inconclusive measurement must not silently become proof that the release is healthy.

### Statistical limitation

Even five successful observations do not establish universal correctness.

A rare defect may require substantial traffic or targeted synthetic testing to detect.

For a robust canary strategy, also consider:

- Baseline-versus-canary comparison.
- Confidence and sample size.
- Request mix.
- Geographic distribution.
- Business metrics.
- Dependency behavior.

### Important principle

> **Canary safety depends more on the quality of its evidence and decisions than on the number of rollout steps.**

# Part XI — Failure and Recovery in Progressive Delivery

## 63. Aborting a canary is not the same as reverting Git

Suppose the canary begins returning errors.

You decide to stop it.

Argo Rollouts supports an abort operation:

```bash
kubectl argo rollouts abort \
  canary-demo \
  -n "$NS"
```

### What is the purpose?

To stop the current progressive rollout and preserve or restore stable serving behavior according to the rollout strategy and current state.

### But what does Git still declare?

Possibly:

```text
Desired Image:
v2
```

### Why is this important?

Because we now have an important distinction.

**Operational abort:** Stop an unsafe in-progress transition.

**GitOps recovery:** Change the authoritative desired artifact back to a safe, approved version when that is the recovery decision.

Aborting a Rollout does not automatically create a Git revert.

### Recovery architecture

```mermaid
flowchart TD
    A["Canary v2 Exhibits Failure"]
    B["Abort Current Rollout"]
    C["Protect Stable Traffic"]

    D["Investigate Compatibility"]
    E["Authorize Recovery"]
    F["Revert GitOps Desired Image to v1"]
    G["Argo CD Reconciliation"]
    H["Verify Stable Application"]

    A --> B
    B --> C

    C --> D
    D --> E
    E --> F
    F --> G
    G --> H
```

### Important nuance

The exact runtime behavior after abortion depends on whether the Rollout is canary or blue-green, whether traffic routing is configured, and which promotion stage has been reached.

Do not treat `abort` as a universal restoration of all application, database, and traffic state.

For a durable GitOps recovery, restore the authorized desired state and verify the result.

## 64. Database compatibility during progressive rollout

Consider a PostgreSQL-backed application.

Version v1 expects:

```text
orders.total_cents
```

Version v2 expects:

```text
orders.amount_cents
```

Now our canary strategy creates a period where both versions are running.

```text
Stable v1:
80%
```

```text
Canary v2:
20%
```

Both versions use the same database.

What happens if we immediately rename the column?

```sql
ALTER TABLE orders
RENAME COLUMN total_cents TO amount_cents;
```

Version v1 may fail.

Even though v2 is healthy.

### The underlying issue

**A progressive rollout creates an intentional mixed-version operating period.**

Therefore, compatibility requirements become more important, not less.

### Safer migration sequence

```mermaid
flowchart TD
    A["Existing v1 and Old Schema"]
    B["Expand Database Schema"]
    C["Deploy Compatible v2 Canary"]
    D["Verify Mixed-Version Operation"]
    E["Promote v2"]
    F["Verify Data Migration"]
    G["Remove Old Application Dependencies"]
    H["Contract Old Schema"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H
```

### Key design questions

- Can v1 read data written by v2?
- Can v2 read data written by v1?
- Can both versions operate during partial data migration?
- Are background workers compatible?
- Can older versions be restored after the migration?
- Does the change introduce irreversible external effects?

### Most important principle

> **A deployment strategy can reduce exposure to application defects, but it cannot compensate for fundamentally incompatible shared-state changes.**

## 65. Feature flags are not deployment strategies

Imagine version v2 contains a new checkout feature.

We deploy v2 successfully.

But we do not want to enable the new checkout experience for everyone.

A feature flag can control exposure independently of the deployed artifact.

### Two different questions

**Deployment strategy:**

Which software version handles a request?

**Feature flag:**

Which feature behavior is enabled for that request or user?

### Architecture

```mermaid
flowchart TD
    A["Application v2 Deployed"]
    B["Feature Flag Decision"]
    C{"Feature Enabled?"}
    D["New Checkout Experience"]
    E["Existing Checkout Experience"]

    A --> B
    B --> C
    C -->|Yes| D
    C -->|No| E
```

### Why is this useful?

It separates:

```text
Deploying New Code
```

From:

```text
Releasing New Functionality
```

A team can deploy compatible code ahead of a feature launch.

However, feature flags introduce their own operational responsibilities:

- Flag ownership.
- Evaluation consistency.
- Cleanup of obsolete flags.
- Configuration availability.
- Testing both enabled and disabled paths.
- Security-sensitive behavior.

### Important distinction

A feature flag can sometimes mitigate a faulty feature without rolling back the entire application.

But it does not replace a deployment recovery strategy for defects outside the flagged functionality.

# Part XII — Designing a Production Deployment Strategy

## 66. Build the strategy from requirements

Imagine your engineering manager says:

> We need zero-downtime deployment for our Node.js API running on AKS.

Don't immediately reply:

> Use canary with Argo Rollouts.

First identify what zero downtime means for the organization.

### Step 1 — Define availability requirements

Ask:

- What is the acceptable request failure rate during deployment?
- What is the current peak request rate?
- How many healthy replicas are required?
- What additional capacity is available?
- Are there latency requirements?

### Step 2 — Define compatibility requirements

Ask:

- Can v1 and v2 run simultaneously?
- Is the API backward-compatible?
- Are database schema changes involved?
- Do background workers process version-sensitive jobs?
- Are external service contracts changing?

### Step 3 — Define exposure requirements

Ask:

- Must the new version be tested before user exposure?
- Is partial user exposure acceptable?
- Must certain customers be excluded?
- Is regional or tenant-specific rollout required?

### Step 4 — Define evidence requirements

Ask:

- Which metrics indicate failure?
- What is the observation window?
- What is the minimum meaningful traffic volume?
- Which business checks must pass?
- What happens when metric collection is unavailable?

### Step 5 — Define recovery requirements

Ask:

- Is the previous image still available?
- Can it operate with the current database?
- Can traffic return to the previous revision?
- Which configuration changes must be reverted?
- Who authorizes recovery?

Only then select a strategy.

### Design process

```mermaid
flowchart TD
    A["Business Requirements"]
    B["Availability Objectives"]
    C["Compatibility Constraints"]
    D["Capacity Constraints"]
    E["Exposure Requirements"]
    F["Verification Requirements"]
    G["Recovery Requirements"]
    H["Choose Deployment Strategy"]
    I["Implement and Test"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H
    H --> I
```

This process applies regardless of whether you use Kubernetes, Azure App Service, AWS ECS, or another runtime platform.

## 68. Deployment strategy and blast radius

The idea of **blast radius** is essential.

It describes the scope of impact when a change causes a failure.

Suppose a bad release causes every request it handles to fail.

If the new version initially handles all requests, potential impact is broad.

If it handles only a small portion of eligible requests, initial impact may be smaller.

Conceptually:

```text
Impact
    ≈
Exposure
    ×
Failure Severity
    ×
Duration
```

This is an engineering intuition, not a rigorous business-impact formula.

### Why canary helps

It attempts to reduce initial exposure.

### Why fast detection helps

It reduces the time before an unsafe change can be stopped.

### Why recovery capability helps

It reduces the duration of unacceptable behavior.

### Why feature flags can help

They may reduce exposure to selected functionality independently from the deployed application version.

### Fundamental insight

> **Production deployment safety improves when we reduce unnecessary exposure, detect failures early, and retain workable recovery options.**

## 69. Resource cost and capacity

Deployment strategies consume different amounts of compute.

Suppose our normal application requires four Pods.

### Recreate

During replacement, capacity can fall to zero before the new Pods become ready.

Additional replacement capacity may be limited, but downtime is possible.

### RollingUpdate

With:

```yaml
maxSurge: 1
```

The rollout can request additional capacity for replacement.

### Blue-Green

Both complete versions may be running simultaneously.

With four replicas per version:

```text
Blue:
4 Pods
```

```text
Green:
4 Pods
```

Temporary total:

```text
8 Pods
```

This can approximately double application-Pod capacity requirements during preview.

### Canary

Capacity depends on:

- The rollout strategy.
- Desired replica count.
- Surge settings.
- Whether traffic routing is configured.
- Whether the stable ReplicaSet remains fully scaled.

For example, with advanced traffic routing, retaining all stable Pods while adding canary Pods can temporarily consume substantially more than steady-state resources.

### Important principle

**A strategy that improves rollout safety can increase infrastructure cost and capacity requirements.**

On AKS, consider:

- Available node CPU.
- Available memory.
- Node autoscaling behavior.
- Pod scheduling constraints.
- Network limits.
- Resource quotas.
- Startup duration.
- Additional node costs.

Do not choose blue-green without checking whether the environment can actually run both versions simultaneously.

## 70. The problem of readiness that lies

Suppose a new application exposes:

```text
/readyz
```

And always returns:

```text
HTTP 200
```

Even when it cannot serve real requests.

Kubernetes considers the Pod ready.

The rollout continues.

Users begin receiving failures.

### What went wrong?

The readiness check did not accurately represent the condition it was supposed to validate.

### Better readiness design

For an API, consider whether the application can:

- Accept connections.
- Initialize required routes.
- Load necessary configuration.
- Access indispensable local resources.
- Safely handle requests.

But avoid blindly checking every external dependency.

If every Pod marks itself unready whenever a shared database experiences a brief interruption, the system may lose all ready endpoints and amplify the outage.

### First-principles lesson

> **Readiness is an application-specific serving contract, not simply an HTTP endpoint that returns success.**

The correct design depends on whether the dependency is necessary for serving the application's intended traffic.

## 71. An important failure: rollback is unavailable

Imagine your canary fails.

The team wants to return to v1.

But v1's image was deleted from the registry.

Or the previous image is incompatible with the current database.

What happens?

The deployment strategy cannot invent a recoverable previous system state.

### Recovery prerequisites

A trustworthy release system should retain:

1. Previous approved artifact identity.
2. Availability of the previous artifact.
3. Previous desired configuration.
4. Relevant database compatibility information.
5. Authorization to perform recovery.
6. Verification procedures.

### What does this mean for GitOps?

The Git history may preserve:

```text
Previous Image Digest
```

But the image must still be available and compatible.

### Fundamental principle

**Deployment history is necessary for recovery traceability, but it is not sufficient to guarantee recoverability.**

## 73. Failure experiment — Canary has insufficient evidence

Suppose we deploy a new version to approximately 5% of traffic.

During the first five minutes:

```text
Canary requests:
20
```

```text
Canary errors:
0
```

Can we conclude that the canary is safe?

No.

Twenty successful requests provide limited evidence about rare failure modes.

The canary may not have encountered:

- A complex checkout.
- A large database transaction.
- A specific customer permission.
- A regional dependency failure.
- High concurrency.
- A rarely used API endpoint.

### Engineering response

Define an evidence policy that considers:

- Representative traffic.
- Minimum observation duration.
- Sufficient request volume.
- Error severity.
- Baseline comparison.
- Synthetic business tests.
- Operational judgment.

### Key lesson

**A canary rollout is only as useful as the behavior it actually observes.**

## 74. Failure experiment — Healthy infrastructure, broken business behavior

Suppose Kubernetes reports:

```text
Ready Replicas:
5
```

Argo CD reports:

```text
Synced
```

Argo Rollouts reports:

```text
Healthy
```

But payment authorization requests fail.

How can this happen?

Because:

- Pods are running.
- Readiness checks pass.
- Deployment configuration matches Git.
- Yet business behavior is incorrect.

### What detects the failure?

Potentially:

- Application metrics.
- Error budgets.
- Synthetic transactions.
- End-to-end tests.
- Business event monitoring.

### What should happen next?

The release decision system should evaluate whether to pause, abort, restore stable traffic, or roll forward.

### Important principle

**Infrastructure health, resource health, and business correctness are different forms of evidence.**

## 75. Failure experiment — Recovery changes the database unexpectedly

Suppose a release uses expand–migrate–contract.

Version v2 begins writing both old and new database fields.

A canary detects a serious issue.

The team restores v1.

If v1 still understands the old field and the migration preserved it, recovery may be straightforward.

Now consider a different release.

Version v2 deletes the old column before the canary completes.

Restoring v1 will not restore the deleted column or its original data.

### Why is this important?

Because **database changes can outlive application deployment changes**.

### Engineering decision

For progressive delivery, prefer compatibility-preserving schema evolution and delay destructive contract changes until old-version dependencies have been safely removed.

This is one reason Phase 09's database migration principles are essential to deployment strategy design.

# 90. Final Understanding

Let's return to our original engineering question:

**How do we introduce a new software version into a running environment while controlling risk and preserving acceptable service behavior?**

We begin with the system's availability, compatibility, exposure, and recovery requirements.

We evaluate whether old and new versions can coexist.

We identify how many healthy instances must remain available.

We verify that the cluster has sufficient capacity.

We define meaningful readiness and graceful termination behavior.

Then we choose an appropriate deployment strategy.

**Recreate** removes the old version before introducing the new one.

**RollingUpdate** gradually replaces old instances with new ones.

**Blue-green** prepares and verifies a replacement version before switching active traffic.

**Canary** introduces a new version to a limited portion of traffic and progressively expands exposure according to policy.

For more advanced progressive delivery, **Argo Rollouts** manages rollout stages, pauses, and analysis.

**Argo CD** remains responsible for reconciling approved desired configuration from Git.

**Kubernetes** maintains the underlying workloads.

**Observability** evaluates whether the new version behaves acceptably.

**Release Engineering** determines which artifact is authorized and which recovery decisions are permissible.

These responsibilities form one production delivery system.

### The most important principle of Phase 13

> **A deployment strategy is a risk-management policy for transitioning a running system between software versions. Its effectiveness depends on capacity, readiness, version compatibility, controlled exposure, trustworthy verification, and viable recovery—not merely Kubernetes configuration.**

That is the difference between knowing the names of deployment strategies and understanding how to engineer them.
