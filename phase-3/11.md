# 2. First Principle: Git Cannot Deploy Software by Itself

Imagine your GitOps repository contains:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ecommerce-api
spec:
  replicas: 3
```

This expresses an intention:

```text
We want three replicas.
```

But Git is a version-control system.

Git does not:

- Authenticate to Kubernetes.
- Create Deployments.
- Watch running Pods.
- Compare Kubernetes resources.
- Investigate image-pull failures.
- Update unhealthy workloads.

Something must interpret the configuration and interact with Kubernetes.

## 2.1 Derive the missing component

We have three existing systems.

**System A: Git**

Stores desired configuration.

**System B: Kubernetes**

Maintains running workloads.

**System C: Container registry**

Stores executable artifacts.

What is missing?

A component that connects approved configuration to the Kubernetes API.

```mermaid
flowchart TD
    A["Git Repository"]
    B["Approved Desired State"]
    C["Missing Control Component"]
    D["Kubernetes API"]
    E["Running Workloads"]

    A --> B
    B --> C
    C --> D
    D --> E
```

That component must be able to:

1. Read the desired configuration.
2. Interpret the configuration.
3. Observe actual Kubernetes state.
4. Identify relevant differences.
5. Perform authorized changes.
6. Recheck the results.
7. Report status.

This is the responsibility of a reconciliation controller.

**Argo CD provides this control system for Kubernetes applications.**

# 3. Argo CD Is Not Just a Deployment Tool

Suppose we compare two systems.

### System A: One-time deployment automation

```text
GitHub Actions
      |
      v
kubectl apply
      |
      v
Kubernetes
```

The pipeline executes and finishes.

### System B: Argo CD reconciliation

```text
Approved Git Configuration
          |
          v
Argo CD
          |
          v
Kubernetes
          |
          v
Observe Actual State
          |
          v
Compare With Git
          |
          v
Repeat
```

The difference is not merely which tool applies YAML.

The difference is the operating model.

## 3.1 Argo CD's fundamental responsibility

> **Argo CD continuously compares Kubernetes resources with declared desired configuration and supports reconciliation according to configured policies.**

Argo CD does not normally compile TypeScript, run application unit tests, or build Docker images.

Those are responsibilities of the CI system.

It does not automatically decide which release is authorized for production.

That is a release engineering decision.

It does not guarantee application business correctness.

That requires runtime verification.

### Engineering principle

**Argo CD manages deployment-state convergence, not the entire software lifecycle.**

# 4. Deriving Argo CD's Internal Architecture

We know the controller must:

- Read Git.
- Generate Kubernetes manifests.
- Compare them with live resources.
- Update Kubernetes.
- Provide an interface for humans.
- Authenticate and authorize users.
- Record reconciliation status.

Should one large process perform every responsibility?

It could, but separating responsibilities makes the architecture easier to scale and operate.

Argo CD uses several cooperating components.

Its official architecture documentation identifies the API server, repository server, and application controller as central components. [Argo CD](https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/?utm_source=chatgpt.com)

# 5. Component One — Repository Server

Imagine the GitOps repository contains:

```text
applications/
└── ecommerce-api/
    ├── base/
    └── overlays/
        ├── dev/
        ├── staging/
        └── production/
```

An Argo CD Application points to:

```text
Repository:
https://github.com/example/release-gitops-lab.git

Revision:
main

Path:
applications/ecommerce-api/overlays/dev
```

How does that become a Kubernetes Deployment and Service?

The repository server is responsible for generating the target manifests from the configured application source.

## 5.1 Its inputs

```text
Repository URL

Git Revision

Application Path

Kustomize or Helm Configuration
```

## 5.2 Its output

```text
Rendered Kubernetes Resource Definitions
```

For example:

```text
Deployment

Service
```

## 5.3 Processing model

```mermaid
flowchart TD
    A["Git Repository"]
    B["Selected Revision"]
    C["Application Path"]
    D["Argo CD Repository Server"]
    E["Kustomize or Helm Processing"]
    F["Rendered Desired Resources"]

    A --> D
    B --> D
    C --> D

    D --> E
    E --> F
```

### Why separate this responsibility?

Because manifest generation is different from modifying Kubernetes.

A repository-server problem may prevent Argo CD from calculating desired state without necessarily affecting an already-running application.

### Example failure

Suppose an overlay contains invalid Kustomize configuration.

The repository server cannot generate the expected manifests.

That is a **manifest-generation failure**.

It is not the same as:

```text
ImagePullBackOff
```

Which happens during runtime image retrieval.

### Engineering lesson

> **Always identify whether a failure occurred before manifest generation, during synchronization, or after Kubernetes accepted the configuration.**

# 6. Component Two — Application Controller

Now suppose the repository server generates:

```text
Deployment:
Image BBB
Replicas 3
```

But Kubernetes currently reports:

```text
Deployment:
Image AAA
Replicas 3
```

What component detects this difference?

The application controller.

## 6.1 Responsibilities

The application controller is responsible for the central reconciliation loop.

It:

- Processes Argo CD Application resources.
- Obtains desired manifests.
- Observes managed Kubernetes resources.
- Compares desired and live state.
- Reports synchronization status.
- Coordinates synchronization operations.
- Evaluates configured health information.
- Processes applicable synchronization hooks and lifecycle operations.

## 6.2 Reconciliation model

```mermaid
flowchart TD
    A["Desired Manifests"]
    B["Live Kubernetes State"]

    C["Application Controller"]
    D["Comparison"]
    E{"Relevant Difference?"}

    F["Synced"]
    G["OutOfSync"]

    H{"Synchronization Permitted?"}
    I["Wait for Manual Sync"]
    J["Execute Reconciliation"]
    K["Observe Result"]

    A --> C
    B --> C

    C --> D
    D --> E

    E -->|No| F
    E -->|Yes| G

    G --> H

    H -->|No| I
    H -->|Yes| J

    J --> K
    K --> C
```

### Important distinction

The application controller works at the deployment-configuration layer.

Kubernetes has its own controllers.

For example:

```text
Argo CD Application Controller
          |
          v
Kubernetes Deployment Resource
          |
          v
Kubernetes Deployment Controller
          |
          v
ReplicaSets and Pods
```

Argo CD does not replace the Kubernetes Deployment controller.

It works with Kubernetes' existing control mechanisms.

Engineers need to interact with Argo CD.

They need to:

- List applications.
- Inspect status.
- View differences.
- Request synchronization.
- Review history.
- Manage application settings.
- Authenticate users.

The Argo CD API server provides the interface for these operations.

## 7.1 Architecture

```mermaid

    B --> D
```

# 8. Other Argo CD Components

Depending on the installation and configuration, you will encounter additional components.

| Component | Purpose |
|---|---|
| Redis | Caching and supporting internal operations |
| ApplicationSet controller | Generates and manages Applications from templates and generators |
| Dex | Supports external authentication integration in applicable configurations |
| Notifications controller | Sends configured application-related notifications |
| Kubernetes CRDs | Extend Kubernetes with Argo CD resources such as `Application` and `AppProject` |

## 8.1 Why use a cache?

Argo CD repeatedly processes Git and Kubernetes information.

Caching can reduce unnecessary repeated work.

But it introduces another operational component.

A cache is not the authoritative source of GitOps desired state.

The selected Git source remains the configuration reference.

## 8.2 Why does ApplicationSet exist?

Imagine an organization has:

```text
20 Applications

3 Environments

Multiple Clusters
```

Manually writing every Argo CD Application object becomes repetitive.

ApplicationSet can generate Applications using predefined inputs and templates.

For example:

```text
Application Template
        +
Cluster or Environment List
        |
        v
Generated Argo CD Applications
```

We will not use ApplicationSet in the initial lab because one Application is enough to understand reconciliation.

### Engineering principle

**Do not introduce additional orchestration abstractions until you understand the object they manage.**

First understand `Application`.

Then understand why `ApplicationSet` exists.

# 10. Understand the Application Manifest

Here is a minimal example.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: ecommerce-dev
  namespace: argocd
spec:
  project: default

  source:
    repoURL: https://github.com/example/release-gitops-lab.git
    targetRevision: main
    path: applications/ecommerce-api/overlays/dev

  destination:
    server: https://kubernetes.default.svc
    namespace: ecommerce-dev
```

Let's examine every field.

### `apiVersion`

```yaml
apiVersion: argoproj.io/v1alpha1
```

This identifies the API group and version of the custom resource.

The Argo CD installation adds the relevant CRDs to Kubernetes.

### `kind`

```yaml
kind: Application
```

This identifies the Argo CD resource type.

### `metadata.namespace`

```yaml
namespace: argocd
```

This is the namespace containing the Application custom resource.

It is not necessarily the namespace where the workload is deployed.

### `spec.project`

```yaml
project: default
```

This selects the Argo CD project that governs the Application.

### `spec.source`

Defines where Argo CD obtains desired manifests.

### `spec.destination`

Defines where Argo CD should apply the rendered resources.

### Why use this server address?

```text
https://kubernetes.default.svc
```

This is the internal Kubernetes API service address used when Argo CD manages its own cluster.

An external cluster requires separate registration and appropriate credentials.

The official getting-started guide distinguishes in-cluster deployment from registering external clusters. [GitHub](https://github.com/argoproj/argo-cd/blob/master/docs/getting_started.md?utm_source=chatgpt.com)

> **An Argo CD Application is a managed group of desired Kubernetes resources, not simply a wrapper around one container or Pod.**

# 12. The AppProject: Authorization Before Reconciliation

Now consider an important security problem.

Suppose any Application can:

- Read any repository.
- Target any cluster.
- Deploy into any namespace.
- Create any Kubernetes resource.

Would that be a good default for a shared production platform?

No.

We need an authorization boundary.

Argo CD provides `AppProject`.

Projects can restrict source repositories, deployment destinations, and permitted or prohibited resources. The built-in `default` project is convenient for testing but is typically too permissive for serious multi-tenant use. [Argo CD](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/?utm_source=chatgpt.com)

## 12.1 Example project

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: ecommerce-dev
  namespace: argocd
spec:
  description: Development application boundary

  sourceRepos:
    - https://github.com/example/release-gitops-lab.git

  destinations:
    - server: https://kubernetes.default.svc
      namespace: ecommerce-dev
```

This establishes permitted source and destination relationships.

### Important limitation

An AppProject is not a replacement for Kubernetes RBAC.

It constrains what Argo CD Applications in the project are permitted to manage.

The Argo CD controller also needs suitable Kubernetes permissions to perform the authorized operations.

A complete security model requires both controls.

## 12.2 Three authorization layers

```mermaid
flowchart TD
    A["Git Repository Authorization"]
    B["Approved Desired-State Change"]
    C["Argo CD AppProject Policy"]
    D["Application Reconciliation"]
    E["Kubernetes RBAC"]
    F["Permitted Kubernetes Modification"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
```

Each layer answers a different question.

**Git:** Who can change approved deployment intent?

**AppProject:** Which sources and destinations may this Argo CD Application use?

**Kubernetes RBAC:** Which operations can the controller identity perform?

### Engineering principle

**Trust requires controlling both the input to the controller and the authority held by the controller.**

# 13. Argo CD Synchronization vs Health

This was one of the most important concepts in Phase 10.

Now let's understand how Argo CD represents it.

Suppose Git declares:

```text
Image: Digest BBB
Replicas: 3
```

Kubernetes contains:

```text
Image: Digest BBB
Replicas: 3
```

But the image cannot be pulled.

Is the application synchronized?

The desired and live configuration may match.

Is it healthy?

No.

Argo CD separately evaluates synchronization and resource health. Its health model supports statuses such as `Healthy`, `Progressing`, `Degraded`, `Suspended`, `Missing`, and `Unknown`. [Argo CD](https://argo-cd.readthedocs.io/en/stable/operator-manual/health/?utm_source=chatgpt.com)

## 13.1 Synchronization status

Typical states include:

| Status | Meaning |
|---|---|
| `Synced` | Managed live configuration matches the desired configuration under comparison rules |
| `OutOfSync` | Relevant live configuration differs from desired state |
| `Unknown` | Comparison cannot establish a normal result |

## 13.2 Health status

Typical states include:

| Status | Meaning |
|---|---|
| `Healthy` | Resource health rules consider the state acceptable |
| `Progressing` | The resource is still moving toward an expected condition |
| `Degraded` | A problem is detected |
| `Suspended` | The resource is intentionally suspended |
| `Missing` | An expected resource is missing |
| `Unknown` | Health cannot be determined |

Not every resource uses every health status.

Custom resources may need custom health rules.

## 13.3 Combined interpretation

| Sync | Health | Possible interpretation |
|---|---|---|
| Synced | Healthy | Desired configuration matches and resource checks are satisfied |
| Synced | Progressing | Configuration matches, rollout is still progressing |
| Synced | Degraded | Configuration matches, but workload reports a problem |
| OutOfSync | Healthy | Existing workload may be healthy, but configuration differs from Git |
| OutOfSync | Progressing | Reconciliation or rollout may still be underway |
| Unknown | Unknown | Repository, comparison, or observation problems may exist |

### Most important principle

> **Argo CD synchronization status describes configuration convergence. It is not a universal measurement of application correctness.**

Even `Synced` and `Healthy` together do not guarantee that all customer transactions succeed.

That is why we also need application-level monitoring.

# 14. Manual Sync, Auto-Sync, Self-Heal, and Prune

These are four related but different ideas.

## 14.1 Manual synchronization

Argo CD detects differences.

An authorized operator explicitly requests synchronization.

Useful when:

- Deployment timing matters.
- The environment requires operator control.
- Automatic production updates are not appropriate.

## 14.2 Automated synchronization

Argo CD automatically attempts synchronization when eligible differences are detected.

Useful when:

- Approved Git changes should progress without another deployment command.
- The repository's authorization process is sufficiently controlled.

## 14.3 Self-healing

Argo CD can attempt to restore desired state when a live-only change causes drift.

Example:

```text
Git:
Replicas = 1

Live:
Replicas = 2
```

With suitable self-healing configuration, the controller may restore one replica.

## 14.4 Pruning

Argo CD can delete previously managed resources that no longer appear in desired state.

This can be useful for removing obsolete resources.

But deletion can also be destructive.

### Configuration examples

Manual synchronization:

```yaml
syncPolicy:
  syncOptions:
    - FailOnSharedResource=true
```

Automated synchronization without self-healing or automatic pruning:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: false
    selfHeal: false
```

Automated synchronization with self-healing:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: false
    selfHeal: true
```

Automated pruning:

```yaml
syncPolicy:
  automated:
    enabled: true
    prune: true
    selfHeal: true
```

For our first lab, **we will begin with manual synchronization**.

Then we will enable automation and deliberately introduce drift.

Argo CD documents these controls separately, including the safeguards around pruning and the fact that self-healing is not enabled automatically merely by enabling auto-sync. [Argo CD](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/?utm_source=chatgpt.com)

# 25. Lab Part I — Create the Argo CD Application

Create:

```text
argocd/bootstrap/dev-app.yaml
```

Add:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: ecommerce-dev
  namespace: argocd
spec:
  project: ecommerce-dev

  source:
    repoURL: https://github.com/YOUR_OWNER/release-gitops-lab.git
    targetRevision: main
    path: applications/ecommerce-api/overlays/dev

  destination:
    server: https://kubernetes.default.svc
    namespace: ecommerce-dev

  syncPolicy:
    syncOptions:
      - FailOnSharedResource=true
```

Replace `YOUR_OWNER`.

## 25.1 Why `targetRevision: main`?

Because the controller should follow the authoritative branch containing approved development configuration.

When `main` changes, Argo CD can observe the new revision.

### Important distinction

`main` is a moving Git reference.

The individual commits it identifies are separate, immutable Git objects.

For a controlled production release, the GitOps repository's approval rules determine which commit may become authoritative.

## 25.2 Why start without automated synchronization?

Because we want to observe the state comparison before allowing Argo CD to modify our application resources.

This makes the control-loop stages visible.

## 25.3 Why use `FailOnSharedResource=true`?

Because our lab should not silently let an Application take over a resource already managed by another Argo CD Application.

This is a resource-ownership safeguard.

Argo CD documents this synchronization option. [Argo CD](https://argo-cd.readthedocs.io/en/latest/user-guide/sync-options/?utm_source=chatgpt.com)

### Important limitation

This does not guarantee protection against every possible controller conflict.

For example, an unrelated Kubernetes operator may manage fields within the same object.

Field ownership still requires separate design.

## 28.2 What should happen internally?

```mermaid
flowchart TD
    A["Operator Requests Sync"]
    B["Argo CD API Server"]
    C["Application Controller"]
    D["Repository Server"]
    E["Rendered Desired Resources"]
    F["Kubernetes API"]
    G["Deployment and Service"]
    H["Kubernetes Deployment Controller"]
    I["Application Pods"]

    A --> B
    B --> C

    C --> D
    D --> E
    E --> C

    C --> F
    F --> G
    G --> H
    H --> I
```

This is the real control flow.

### Step 1: Read desired state

Argo CD retrieves and processes the configured Git revision.

### Step 2: Render configuration

The repository server generates Kubernetes resources from the Kustomize overlay.

### Step 3: Compare

The application controller compares desired resources with observed live resources.

### Step 4: Synchronize

The controller requests Kubernetes API changes.

### Step 5: Reconcile workloads

Kubernetes controllers create or update the necessary workload resources.

### Step 6: Retrieve the image

The Kubernetes node's container runtime retrieves the selected image if required.

### Step 7: Report results

Argo CD observes synchronization and resource-health information.

### Important distinction

Argo CD does not pull the container image into the application Pod itself.

That operation belongs to Kubernetes and its container runtime.

# 36. The Important HPA Ownership Problem

Before moving forward, consider a production system.

Suppose an HPA is responsible for scaling the application.

The HPA requests:

```text
Replicas: 5
```

But Git defines:

```text
Replicas: 1
```

And Argo CD has self-healing enabled.

We may create competing control loops.

## 36.1 Conflict

```mermaid
flowchart TD
    A["GitOps Desired Replicas: 1"]
    B["Argo CD"]

    C["CPU Utilization"]
    D["Horizontal Pod Autoscaler"]

    E["Deployment Replica Field"]

    A --> B
    B -->|"Reconcile to 1"| E

    C --> D
    D -->|"Scale to 5"| E
```

### What is the underlying problem?

Two controllers are trying to own the same effective field.

### How should we solve it?

Define field ownership.

For example, if the autoscaler legitimately owns the replica count, Argo CD should be configured to account for that ownership.

Argo CD supports `ignoreDifferences` and related synchronization settings.

For example:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      name: ecommerce-api
      jsonPointers:
        - /spec/replicas

  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

**Do not apply this change to our current lab.** We intentionally want Git to own the replica count for the drift experiment.

Also, ignoring a difference in comparisons is not identical to ignoring it during synchronization; `RespectIgnoreDifferences=true` affects how ignored differences are handled during sync. Argo CD documents this distinction. [Argo CD](https://argo-cd.readthedocs.io/en/stable/user-guide/diffing/?utm_source=chatgpt.com)

### Fundamental principle

**Every reconciled resource field should have a clear authoritative owner.**

**A Git deletion is a proposed change to desired state. It should not be treated as risk-free simply because it is declarative.**

# 48. Argo CD Application Lifecycle and Deletion

Now consider a more subtle question.

What happens when an Argo CD Application itself is deleted?

There are two different objects to think about:

1. The Argo CD Application custom resource.
2. The Kubernetes resources managed by that Application.

Deleting the Application object may or may not delete its managed resources, depending on deletion mode, finalizers, and applicable ownership behavior.

This distinction matters for GitOps bootstrap and decommissioning.

## 48.1 Conceptual lifecycle

```mermaid
flowchart TD
    A["Application Object"]
    B["Managed Kubernetes Resources"]
    C["Application Deletion Requested"]
    D{"Cascading Deletion Configured?"}
    E["Remove Managed Resources"]
    F["Leave Resources Orphaned"]

    A --> B
    A --> C

    C --> D

    D -->|Yes| E
    D -->|No| F
```

### What is the operational concern?

An engineer might intend to stop Argo CD from managing an application.

But deleting the Application with cascading deletion can also remove the workloads.

Those are materially different intentions.

### First-principles lesson

> **Changing controller ownership and deleting runtime resources should be modeled as separate lifecycle decisions.**

Do not experiment with deleting the Application until you understand the expected cleanup behavior.

# 50. The GitOps Bootstrap Problem

We have now installed Argo CD and created an Application.

But think about how we did it.

We used:

```bash
kubectl apply -f argocd/bootstrap/dev-app.yaml
```

Is that GitOps?

The application's deployment resources are managed through GitOps.

But the bootstrap Application resource was installed manually.

This leads to an interesting question:

**Who manages the GitOps controller and its own configuration?**

## 50.1 Possible designs

### Design A: Manual initial bootstrap

An operator installs Argo CD and creates the first Application.

After that, Argo CD manages application resources.

This is what our lab does.

### Design B: Root Application

A root Argo CD Application tracks Git configuration that defines other Argo CD Applications.

Conceptually:

```mermaid
flowchart TD
    A["Bootstrap Root Application"]
    B["GitOps Repository"]
    C["Application Definitions"]

    D["Development Application"]
    E["Staging Application"]
    F["Production Application"]

    A --> B
    B --> C

    C --> D
    C --> E
    C --> F
```

This is often called an **App-of-Apps** pattern.

It introduces its own trust and ownership considerations.

### Design C: ApplicationSet

An ApplicationSet resource generates and manages Applications using templates and generators.

This is useful for repeated patterns across applications, environments, or clusters.

## 50.2 Which design should we use?

For the current learning project:

**Manual bootstrap followed by GitOps-managed application configuration is sufficient.**

For a larger platform, Root Application or ApplicationSet may reduce repeated setup and improve consistency.

### Important warning

A root Application that can generate or manage many child Applications has significant authority.

Treat its repository and configuration as privileged infrastructure.

# 52. Diagnosing Argo CD With a Failure-Boundary Matrix

A production engineer should avoid debugging by randomly changing configuration.

Use a systematic model.

| Symptom | Likely boundary | First investigation |
|---|---|---|
| Application does not appear | Application creation | Check Application CR and namespace |
| Invalid repository error | Git authentication or URL | Check `repoURL`, credentials, repository-server logs |
| Manifest generation error | Kustomize or Helm | Render configuration locally and inspect repo-server logs |
| AppProject permission error | Argo CD project policy | Inspect allowed sources and destinations |
| Synchronization fails | Kubernetes API or resource admission | Inspect sync operation and resource messages |
| `OutOfSync` persists | Configuration difference or reconciliation policy | Inspect live-versus-desired diff |
| `Synced` but Pod cannot start | Image/runtime boundary | Inspect Pod events and image pulls |
| Pod crashes | Application runtime | Inspect container logs |
| Pods ready but API fails | Application behavior | Run API checks and inspect dependencies |
| Manual changes repeatedly revert | Self-healing or another controller | Identify field ownership and reconciliation policy |
| Resources unexpectedly deleted | Pruning or deletion lifecycle | Inspect sync history, Git changes, and finalizers |
| Controller cannot process changes | Argo CD infrastructure | Inspect controller health, logs, and connectivity |

## 52.1 A repeatable debugging process

```mermaid
flowchart TD
    A["Deployment Problem"]
    B["Identify Expected Git Revision"]
    C["Check Application Source"]
    D["Verify Manifest Generation"]
    E["Inspect Sync Result"]
    F["Inspect Kubernetes Resources"]
    G["Inspect Container Runtime"]
    H["Run Application Verification"]
    I["Identify First Failed Boundary"]

    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> G
    G --> H
    H --> I
```

Do not assume every investigation must traverse every step.

Once the first failed boundary is identified, focus on the evidence relevant to that failure.

### Example

If Argo CD cannot authenticate to Git, debugging container startup logs is probably premature.

If Git rendering and synchronization succeed, but the Pod is in `ImagePullBackOff`, investigate registry access rather than rewriting Kustomize.

### Engineering principle

> **Debug GitOps as a chain of contracts: source retrieval, manifest generation, authorization, synchronization, Kubernetes reconciliation, artifact retrieval, and application behavior.**

## 53.4 Compare desired and live state

```bash
argocd app diff ecommerce-dev
```

A successful command with no differences indicates that no relevant difference was found under the current comparison rules.

## 53.5 Request synchronization

```bash
argocd app sync ecommerce-dev
```

This explicitly requests a synchronization operation.

Use it when an operator is authorized to perform the action.

## 53.6 Wait for synchronization and health

```bash
argocd app wait ecommerce-dev \
  --sync \
  --health \
  --timeout 180
```

This waits for the specified Application conditions.

### Important qualification

Passing both conditions does not prove every business transaction works.

Application-level smoke tests and runtime monitoring remain separate requirements.

# 54. Production Engineering — How Should Argo CD Be Operated?

Our local installation is suitable for learning.

Production introduces additional requirements.

## 54.1 Availability

Ask:

- What happens if the application controller becomes unavailable?
- What happens if Redis fails?
- What happens if the repository server cannot reach Git?
- What happens during a Kubernetes API outage?
- How will critical controller components be monitored?

For an environment with higher availability requirements, evaluate Argo CD's supported high-availability architecture.

## 54.2 Authentication and authorization

Ask:

- Who can log in?
- Which teams may view applications?
- Which teams may synchronize production?
- Who can modify Projects?
- Who can register clusters?
- Who can change repository credentials?
- Can users bypass release review through the UI?

## 54.3 Resource ownership

Ask:

- Which Applications own which Kubernetes resources?
- Are resources shared between applications?
- Does another operator manage the same fields?
- Are deletion and pruning behaviors understood?
- Are autoscaling controllers compatible with the chosen diff rules?

## 54.4 Security

Ask:

- Are trusted Git repositories restricted?
- Are controller permissions appropriately scoped?
- Are repository and registry credentials protected?
- Is Argo CD publicly exposed?
- Are TLS and identity integrations configured?
- Are Argo CD upgrades and security patches maintained?
- Is production desired state protected by review policies?

## 54.5 Observability

Ask:

- Can we detect persistent `OutOfSync` states?
- Can we detect failed synchronization?
- Can we distinguish source-access problems from Kubernetes errors?
- Are controller logs available?
- Are reconciliation delays observable?
- Are application health and business metrics monitored separately?

### Engineering principle

**Argo CD is part of the production delivery control plane. It requires reliability and security engineering just like the systems it manages.**

# 55. Metrics for Evaluating GitOps Quality

How do we know whether the GitOps architecture is working well?

A useful system should provide evidence about delivery-state convergence.

| Metric | What it helps evaluate |
|---|---|
| Time from approved Git commit to detection | Source-refresh latency |
| Time from detection to successful synchronization | Reconciliation latency |
| Time from synchronization to workload readiness | Runtime convergence |
| Failed synchronization frequency | Deployment-control reliability |
| Persistent `OutOfSync` duration | Unresolved configuration differences |
| Controller availability | GitOps control-plane reliability |
| Repository access failures | Desired-state retrieval problems |
| Unauthorized drift incidents | Configuration governance |
| Time to restore approved desired state | Recovery efficiency |
| Application error rate after releases | Operational release quality |

### Important distinction

A fast Argo CD synchronization does not automatically imply fast application readiness.

For example:

```text
Argo CD Sync:
Successful
```

But:

```text
Container Startup:
3 minutes
```

And:

```text
Database Migration:
10 minutes
```

These are different parts of the delivery process.

### First-principles lesson

> **Measure the complete state transition from approved intent to acceptable runtime behavior, not just the time taken by the synchronization command.**

# 63. Final Understanding — The Complete Argo CD System

Let's return to the central question:

**How does Argo CD transform an approved Git commit into an actual Kubernetes application?**

The process begins with a GitOps Application.

The Application identifies:

- Which repository Argo CD should read.
- Which revision it should track.
- Which path contains the desired resources.
- Which cluster and namespace should receive them.
- Which AppProject governs the Application.
- Which synchronization policies are enabled.

The repository server generates the desired Kubernetes manifests.

The application controller compares them against Kubernetes live resources.

It reports the relevant differences.

If synchronization is authorized, Argo CD requests the necessary Kubernetes changes.

Kubernetes controllers then work toward the requested workload state.

The container runtime obtains the selected image.

The application starts.

Argo CD evaluates synchronization and supported resource-health information.

Application-level verification determines whether the running software behaves acceptably.

This is the complete control loop.
